## What was actually wrong

The open item read "the store's 404 page has never been styled". It was worse than that, and it was
not only the store.

Four routes answered with an empty document — `<html id="__next_error__">`, no stylesheet, no text,
no `lang`. The page appeared only after JavaScript hydrated, and not at all without it. Verified on
production, not just locally:

| URL | Status | Stylesheets | Server-rendered text |
|---|---|---|---|
| `store.kheelona.com/<typo>` | 404 | **0** | **none** |
| `store.kheelona.com/store` | 404 | **0** | **none** |
| `kheelona.com/stories/<unknown-slug>` | 404 | **0** | **none** |
| `store.kheelona.com/thanks` with a valid link to a missing order | 404 | **0** | **none** |
| *control:* `kheelona.com/<typo>` | 404 | 1 | full |

The third row is a **public marketing URL pattern**. The fourth is the one that matters most: a
person who had paid us, whose confirmation link was correctly signed, looking for their own order.

## Why the control row is the whole diagnosis

`kheelona.com/typo` rendered fine while `kheelona.com/stories/typo` did not, and the difference is
not in this app's code. `notFound()` throws; `app-render` catches it and answers with
`getErrorRSCPayload`, described in Next's own source as *"the data necessary to render `<AppRouter />`
when an error state is triggered"* — a client-rendered shell. A URL matching **no route** never
enters that path.

16.3.4 was the latest release. There was nothing upstream to wait for.

## Two fixes, because the two cases are not the same

**`/stories/[slug]` — `export const dynamicParams = false`.** An unlisted slug stops at the router,
which renders the marketing 404 exactly as it always did for other unknown URLs. One line, no
trade-off, and the correct chrome falls out for free.

**The store — the page renders and the proxy supplies the status.** Routing-level 404 was tried and
rejected: it renders, but it serves the MARKETING 404 on the payment host, which is what
`[...rest]` was added to prevent. A `loading.tsx` Suspense boundary was tried and rejected: it
renders the chrome but turns the status into 200 and leaves the body streaming.

What works is `NextResponse.rewrite(url, { status: 404 })`, probed before being designed around:
404 status, full server-rendered body. So the pages became ordinary pages and `src/proxy.ts` carries
the status, which it can do because `lib/store/host.ts` knows the path is not a store page before
Next resolves anything.

The founder chose this over the simpler "render it and accept 200", having been shown that the
correct-status route means editing the checkout host's routing.

## The cost of that choice, and what pays for it

`STORE_PAGES` restates what the folders under `src/app/store/` already say. **Tightening is the
dangerous direction** — a list missing a page 404s a live checkout page, and no visitor reports
that.

So the guard walks the filesystem rather than the list: `store-host.test.ts` reads
`src/app/store/`, turns each `page.tsx` into the URL a visitor would type, and asserts the proxy
admits every one. Proven red by dropping `/ideabaaz`:

```
AssertionError: /ideabaaz exists but the proxy would 404 it: expected false to be true
```

## Three things found while fixing it

**1. `/thanks` threw at a paying customer.** `if (!data) notFound()` fires when a validly signed
link points at an order that will not load. Now a panel with WhatsApp and **no "buy again" button**,
because sending someone who already paid back to the buying page is the wrong offer.

**2. A latent bug, deliberately left.** `maybeSingle()` returns a null `data` both when the row is
missing and when the query failed, so a transient Supabase outage looks identical to a deleted
order. Logged in `Technical-Todo.md`; the copy was written to be honest under both readings.

**3. `/404-store-path` was deleted, not fixed.** It rendered the marketing 404 on the payment host,
and the catch-all already covers the doubled `/store` prefix it existed for.

## Campaign tagging got a mechanism

`docs/utm-conventions.md` had been the whole of it, and a doc enforces nothing while
`utm_campaign` reads 100% "Direct / None" and a Meta Pixel runs for paid social.

`npm run utm` builds a link or refuses and names the rule. `test/utm.test.ts` parses the doc's
parameter table so the tool and the doc cannot drift, and asserts the doc's worked example is
byte-for-byte what the tool emits.

**The guard found something good.** Its first version banned `utm_` anywhere in `src/` and flagged
two payment files — both of which **read** UTM values off the landing URL to record which campaign
produced an order. That capability was documented nowhere. The detector now distinguishes writing a
tag from reading one, both directions are asserted, and the capture behaviour has its own test.

**Diffs that are the real gate:**

- **Server answers: exactly four rows changed**, all `css=0` → `css=1`. Every other row — statuses,
  redirect destinations, `x-robots-tag`, all six security headers — byte-identical.
- **Generated CSS byte-identical**, 60164 bytes, same digest.
- **Bundle digest identical.** Nothing that ships to the browser moved, which is the proof that no
  client component changed.
- **Prerendered head diff: removals only**, and the only removal is the deleted `/404-store-path`.
  Zero additions across all remaining pages.
- **Route manifest**: 21 redirects, 1 headers entry, 3 rewrites — unchanged.
- **Claim path re-driven attribute by attribute**: 303, `Location: /thanks` with the query stripped,
  `Set-Cookie: kh_order=…; Path=/thanks; Max-Age=7200; HttpOnly; SameSite=lax`,
  `cache-control: private, no-store`. (`Secure` is deliberately off on localhost and on there.)

That last one cost a detour worth recording: the first attempt returned 200, and the reflex was to
suspect the change. The token was wrong — `sign()` truncates the HMAC to 16 characters and the probe
used the full 43-character digest, so it failed `TOKEN_SHAPE` and fell through. **The verification
tool was the broken thing, again.**

# Addendum, same day: the fix was half wrong, and the deploy is what said so

**Commit `TBD`. The store now answers 200 with its own chrome, not 404 with the marketing site's.**

`NextResponse.rewrite(url, { status: 404 })` was probed under `npx next start`, where it returns
404 AND the rewritten page. **Vercel's edge does not do that.** It sees the 4xx, discards the
destination and serves its own `/404` — the ROOT not-found, which is the marketing site's. Verified
on production after the deploy:

```
$ curl -sD- https://store.kheelona.com/typo-page
HTTP/2 404
x-matched-path: /404          <- not /store/typo-page
x-robots-tag: noindex, nofollow   <- so the proxy DID run
```

So the round shipped the one outcome it had explicitly rejected: the marketing navbar on the payment
host (§8.25-z). Better than the blank page it replaced, and worse than what was promised.

**What was wrong was the verification, not the reasoning.** The trilemma table in this checkpoint is
still correct for `next start`; it is wrong for the platform this site runs on. The founder chose
"complete fix" on the strength of a probe that did not test the deployment target.

The fix is the option originally recommended and then talked out of: **drop the status.** Vercel
honours the destination, the catch-all renders the store's own not-found inside the store chrome,
and it answers 200 — a soft 404 on a host that is `noindex, nofollow`, absent from the sitemap and
never crawled for ranking, so nothing measurable reads it.

`STORE_PAGES` and `isStorePage` went with it. They existed only to tell the proxy which paths
deserved the status, and dead routing knowledge on the host that takes money is a liability, not a
spare part. `routeForHost` is now simpler than it was before this round began — the claim branch,
then one rewrite — because the `/404-store-path` special case is gone too.

| | Before the round | After the first fix (live 15:15) | After the addendum |
|---|---|---|---|
| Renders | ✗ blank | ✓ | ✓ |
| Chrome on the store host | store, client-only | **marketing** ✗ | **store** ✓ |
| Status | 404 | 404 | 200 |
| Routing knowledge duplicated | no | yes | **no** |

Marketing side unaffected throughout: `/stories/<unknown>` and `/typo` both 404 with the full
marketing 404, which is the correct chrome there.

**The lesson is §8.34-f, and it is bigger than this bug:** `next start` is not the deployment
target. A local probe settles what Next does and nothing about what Vercel's edge does with the
result. This repo cannot deploy — Vercel is the founder's — so anything resting on proxy response
semantics is *pending a deploy*, and saying so is part of the work.
