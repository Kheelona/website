## Why this round exists

The founder set up a PostHog account (project **617632**, US cloud) and asked for it to be
integrated. PostHog is the **fifth** measurement tool on this site, after Vercel Web Analytics
(2026-07-28), Ahrefs (2026-07-30), GA4 (2026-07-28) and the Meta Pixel (2026-09-01).

## The four decisions, taken in one question round on 2026-09-19

| | Decision | Consequence |
|---|---|---|
| Scope | **Product analytics + session replay + error tracking** | The largest privacy surface of any tool here. Drives most of this document |
| Autocapture | **On** | PostHog records every click and form interaction sitewide, with no per-element code |
| Relationship to GA4 | **Additive for now** | Five tools run in parallel. No GA4 retirement in this round |
| API key | Hardcoded in `config/site.ts` | NOT a Vercel secret — see below |

### The key is hardcoded, and the founder's offer of a Vercel secret was declined for a reason

The founder offered to set a Vercel secret. A PostHog **project API key** (`phc_…`) is a public
client-side identifier: PostHog's own snippet ships it in the page, exactly like the GA4 measurement
ID and the Meta Pixel ID already hardcoded beside it. It is not a credential and it authorises
nothing but writing events into the project it names.

More to the point, the repo has already paid for this lesson twice (§8.30): a `NEXT_PUBLIC_` name
**cannot** be a Vercel Secret, because the value is inlined into the browser bundle at build time,
which is precisely what the dashboard refuses. `NEXT_PUBLIC_GA4_MEASUREMENT_ID` was retired for the
same reason. So the key sits in `src/config/site.ts` with a comment explaining why that is safe, and
`POSTHOG_HOSTS` is what actually protects the project from localhost and preview traffic.

### The wizard was not used, and that was deliberate

PostHog's onboarding offers `npx @posthog/wizard self-driving`, which detects the framework,
installs the SDK and opens pull requests. It was declined. This repo has binding structure laws it
could not know about: `src/`-based atomic design with a colocated Storybook story and Vitest test per
component, a hand-written CSP in `src/lib/security-headers.ts`, and **§8.21-c** — adding a
measurement tool means editing `/privacy` in the *same commit*, enforced by
`test/analytics-tags.test.ts`, which counted four tools before this round. An agent wiring the SDK
its own way would have shipped a tag without its disclosure.

### Commit 1 — the dependency, the identifiers, and one advisory judged rather than waved

`posthog-js@1.434.2`, installed with `--save-exact` (the pin law, §8.35-2). **Nothing existing
moved**: all twelve lockfile entries are pure additions, verified by diffing `packages` before and
after rather than trusting the installer's summary.

`src/config/site.ts` gains `POSTHOG_KEY`, `POSTHOG_API_HOST`, `POSTHOG_ASSET_HOST`,
`POSTHOG_HOSTS` (= `GA4_HOSTS`), `POSTHOG_REPLAY_DENY_PATHS`, `shouldLoadPostHog()` and
`replayAllowedOnPath()`.

#### `npm audit` reads 2 moderate, and they are NOT PostHog's

`@vitest/mocker` / `vitest`, GHSA-82fw-gwwq-j7x9, path traversal via a redirect mock. `vitest` does
not appear in the moved-packages diff, so this is a **pre-existing dev-only advisory published since
the 2026-09-05 sweep**, surfaced because `npm install` re-runs the audit. posthog-js introduced
zero. Queued in `Technical-Todo.md` rather than fixed here: it is dev-only, it never ships, and this
repo's law is that dependency moves are decided deliberately, not ridden along in an unrelated round.

#### The dependency floor caught a real thing, and the fix was NOT an override

`test/dependency-floor.test.ts` failed immediately: posthog-js pins `fflate ^0.4.8` and ships a
nested **0.4.9**, below the 0.6.11 floor recorded for GHSA-px8p-9vwx-vf98 (`unzipSync` infinite loop
on a malformed ZIP64 archive).

**Verified against the shipped code rather than assumed.** The only fflate identifiers anywhere in
`posthog-js/dist` are `gzipSync` (17), `strToU8` (17) and `strFromU8` (7). `unzipSync` appears in no
posthog-js file — only inside fflate's own library files, which ship the function whether or not
anyone calls it. PostHog uses fflate to COMPRESS outbound session-replay payloads and never
decompresses an untrusted archive, which is the whole attack surface of the advisory.

An npm `override` would have been the wrong fix, for exactly the reason this repo carries **zero**
of them (§8.35-3, the postcss/sharp case): **0.6.11 does not satisfy posthog-js's `^0.4.8`**, so
forcing it would ship a combination PostHog has never tested.

So the floor gained a **path-exact exemption** carrying that verified reasoning, plus a new guard
that keeps the exemption honest. It fails if the exempt path leaves the lockfile, if the exempt copy
comes to satisfy the floor on its own (a stale excuse left lying around to cover a future
downgrade), or if the reason is too short to be one. Path-exact on purpose: the same package
arriving under a different parent is still a failure.

**Both failure modes were mutation-tested rather than trusted** — the path mutation and the
already-meets-floor mutation each failed with the intended message, and the restored file passed.
