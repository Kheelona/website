## Why this round exists

The founder set up a PostHog account (project **617632**, US cloud) and asked for it to be
integrated. PostHog is the **fifth** measurement tool on this site, after Vercel Web Analytics
(2026-07-28), Ahrefs (2026-07-30), GA4 (2026-07-28) and the Meta Pixel (2026-09-01).

## The four decisions, taken in one question round on 2026-09-19

| | Decision | Consequence |
|---|---|---|
| Scope | **Product analytics + session replay + error tracking** | The largest privacy surface of any tool here. Drives most of this document |
| Autocapture | **On** | PostHog records every click and form interaction sitewide, with no per-element code |
| Relationship to GA4 | **Additive for now** | Five tools run in parallel. No GA4 retirement in this round |
| API key | Hardcoded in `config/site.ts` | NOT a Vercel secret — see below |

### The key is hardcoded, and the founder's offer of a Vercel secret was declined for a reason

The founder offered to set a Vercel secret. A PostHog **project API key** (`phc_…`) is a public
client-side identifier: PostHog's own snippet ships it in the page, exactly like the GA4 measurement
ID and the Meta Pixel ID already hardcoded beside it. It is not a credential and it authorises
nothing but writing events into the project it names.

More to the point, the repo has already paid for this lesson twice (§8.30): a `NEXT_PUBLIC_` name
**cannot** be a Vercel Secret, because the value is inlined into the browser bundle at build time,
which is precisely what the dashboard refuses. `NEXT_PUBLIC_GA4_MEASUREMENT_ID` was retired for the
same reason. So the key sits in `src/config/site.ts` with a comment explaining why that is safe, and
`POSTHOG_HOSTS` is what actually protects the project from localhost and preview traffic.

### The wizard was not used, and that was deliberate

PostHog's onboarding offers `npx @posthog/wizard self-driving`, which detects the framework,
installs the SDK and opens pull requests. It was declined. This repo has binding structure laws it
could not know about: `src/`-based atomic design with a colocated Storybook story and Vitest test per
component, a hand-written CSP in `src/lib/security-headers.ts`, and **§8.21-c** — adding a
measurement tool means editing `/privacy` in the *same commit*, enforced by
`test/analytics-tags.test.ts`, which counted four tools before this round. An agent wiring the SDK
its own way would have shipped a tag without its disclosure.

### Commit 1 — the dependency, the identifiers, and one advisory judged rather than waved

`posthog-js@1.434.2`, installed with `--save-exact` (the pin law, §8.35-2). **Nothing existing
moved**: all twelve lockfile entries are pure additions, verified by diffing `packages` before and
after rather than trusting the installer's summary.

`src/config/site.ts` gains `POSTHOG_KEY`, `POSTHOG_API_HOST`, `POSTHOG_ASSET_HOST`,
`POSTHOG_HOSTS` (= `GA4_HOSTS`), `POSTHOG_REPLAY_DENY_PATHS`, `shouldLoadPostHog()` and
`replayAllowedOnPath()`.

#### `npm audit` reads 2 moderate, and they are NOT PostHog's

`@vitest/mocker` / `vitest`, GHSA-82fw-gwwq-j7x9, path traversal via a redirect mock. `vitest` does
not appear in the moved-packages diff, so this is a **pre-existing dev-only advisory published since
the 2026-09-05 sweep**, surfaced because `npm install` re-runs the audit. posthog-js introduced
zero. Queued in `Technical-Todo.md` rather than fixed here: it is dev-only, it never ships, and this
repo's law is that dependency moves are decided deliberately, not ridden along in an unrelated round.

#### The dependency floor caught a real thing, and the fix was NOT an override

`test/dependency-floor.test.ts` failed immediately: posthog-js pins `fflate ^0.4.8` and ships a
nested **0.4.9**, below the 0.6.11 floor recorded for GHSA-px8p-9vwx-vf98 (`unzipSync` infinite loop
on a malformed ZIP64 archive).

**Verified against the shipped code rather than assumed.** The only fflate identifiers anywhere in
`posthog-js/dist` are `gzipSync` (17), `strToU8` (17) and `strFromU8` (7). `unzipSync` appears in no
posthog-js file — only inside fflate's own library files, which ship the function whether or not
anyone calls it. PostHog uses fflate to COMPRESS outbound session-replay payloads and never
decompresses an untrusted archive, which is the whole attack surface of the advisory.

An npm `override` would have been the wrong fix, for exactly the reason this repo carries **zero**
of them (§8.35-3, the postcss/sharp case): **0.6.11 does not satisfy posthog-js's `^0.4.8`**, so
forcing it would ship a combination PostHog has never tested.

So the floor gained a **path-exact exemption** carrying that verified reasoning, plus a new guard
that keeps the exemption honest. It fails if the exempt path leaves the lockfile, if the exempt copy
comes to satisfy the floor on its own (a stale excuse left lying around to cover a future
downgrade), or if the reason is too short to be one. Path-exact on purpose: the same package
arriving under a different parent is still a failure.

**Both failure modes were mutation-tested rather than trusted** — the path mutation and the
already-meets-floor mutation each failed with the intended message, and the restored file passed.

Gates: **1223 tests / 118 files** (was 1222; the floor's new honesty test), `tsc` 0.

### Commit 2 — the tag, its disclosure and its CSP, as one unit

§8.21-c binds a measurement tool to the sentence describing it, so all of this is one commit:
`src/lib/posthog.ts`, `PostHogGate` with its colocated test and story, the layout mount, the CSP
origins, the `/privacy` rewrite, and `test/analytics-tags.test.ts` counting five.

#### Two things were read out of the SDK rather than believed, and one of them was already wrong

**`ui_host` was set to the asset host in the first draft, and that was a bug.** The installed type
documents it as *"If using a reverse proxy for `api_host` then this should be the actual PostHog app
URL"*, and the router confirms it: `endpointFor("ui", …)` resolves against `uiHost`, which is what
PostHog builds **deep links back to its own dashboard** from — person URLs, recording URLs, and the
tags attached to captured exceptions. Pointing it at a CDN would have produced dead links in the
founder's inbox, silently, with everything else working. It is now **not set at all**, which is
correct for a direct (non-proxied) install.

**The asset origin is derived, not configured.** From the router:

```js
case "assets": return `https://${this.region}-assets.${Qa}`   // Qa = i.posthog.com
```

So `api_host: "https://us.i.posthog.com"` is what produces `us-assets.i.posthog.com`. That origin
appears in no PostHog config anywhere, which makes it exactly the kind of CSP entry that gets
missed — and the symptom would be session replay silently never starting, with the browser refusing
a URL that appears nowhere in this repo. It is pinned in **both** `script-src` and `connect-src`.

Every config option used was checked against `@posthog/types/dist/posthog-config.d.ts` rather than
recalled: `capture_pageview` really does accept `'history_change'`, `person_profiles` really is
`'always' | 'never' | 'identified_only'`, and so on.

#### Four configuration decisions, and why each is written down rather than inherited

| Setting | Value | Why it is stated rather than defaulted |
|---|---|---|
| `disable_session_recording` | `true` at init | The recorder must never start on its own. Replay is turned on **per route**, so a denied route never had a recorder running to leak from. Starting-then-stopping would record the confirmation page for however long the stop took |
| `maskAllInputs` | `true` | PostHog's own default. Written out because inheriting a default on a page where a parent types their phone number is not a decision anyone can later see was made |
| `person_profiles` | `identified_only`, and **no `identify()` call anywhere** | Everyone stays anonymous. Funnels work on the anonymous distinct_id, so nothing is lost but a billable profile per visitor — and no parent's order is welded to a browsing identity |
| the import | dynamic, **after** the host check | A static import would put ~60KB in the shared client bundle on every host, including the ones where the gate is shut and it can never run |

`instrumentation-client.ts` — which this Next version offers and PostHog's own guide prefers — was
**declined**. It runs before the app's frontend code on *every* host, so it would still need the
hostname gate, and it would put an SDK plus a session recorder in front of first paint on a site
whose standing law is that nothing competes with the hero image (§8.19).

#### The privacy page: a new paragraph, not a bigger list

PostHog is a different KIND of tool from the other four. It does not follow anyone between sites and
is never used to advertise — milder than the pixel on both axes. But autocapture records every tap
and replay records the screen, so on *this* site it sees more than the other four together. Filing
that under "analytics" would have been true and useless, so it gets its own paragraph, and three
promises a parent could actually act on:

1. typed values are masked before the recording leaves the browser;
2. the confirmation page is **not recorded at all**;
3. the data is held on servers in the United States.

Promise 2 is the only one on the whole page **enforced by data rather than by care** — a test asserts
that `/privacy` makes the claim AND that `replayAllowedOnPath("/store/thanks")` is still `false`.
Emptying the deny list fails five tests, one of which says exactly that. Mutation-tested.

#### A count was retired rather than bumped

The page said the reader's browser could block *"the three that only run in your browser"*. PostHog
made that false — there are now four — and **a test pinned the sentence**, so the suite would have
gone on enforcing a false claim. That is the identical failure this file was burned by on 2026-09-02
with the "two readable fields" wording. So the number was removed rather than incremented, and both
the old count and *any* future count are banned by regex. A category stays honest at any number of
tools; a count stops being true the moment one is added.

One assertion also had to become conjugation-tolerant: it pinned the literal `"does set cookies"`,
which broke when the sentence correctly became "Google Analytics and PostHog **do** set cookies" — a
test failing on verb agreement while the disclosure it guards got strictly better.

### Commit 3 — the funnel, and the page autocapture must not read

#### PostHog joins the five funnel bodies rather than being left to autocapture

Autocapture is on, so it would already have produced a click event for the pre-order button. That
is not the same thing: **autocapture cannot produce a value in rupees, a tier, or an order
reference**, and a funnel that cannot be set beside the GA4 and Meta ones is worth very little. So
PostHog joins the same five function bodies in `features/preorder/lib/analytics.ts`, reusing the GA4
event names verbatim so all three can be read side by side.

`analytics.test.ts` is new, and it asserts **behaviour rather than spelling**. A source grep for
`phCapture` would count six occurrences and pass happily while one of them sat in the wrong
function. Instead each event is fired and what each tool actually received is recorded, checking two
things per event: that it reached GA4 and PostHog at all, and that **the two payloads are identical**
— because two tools that disagree about the value are worse than one tool.

Both drift modes were mutation-tested: dropping `phCapture` from one event failed with
`dismissed did not reach PostHog`, and feeding PostHog paise where GA4 got rupees failed the
identical-properties assertion. That second one matters — a tool fed paise reports a hundredfold
ROAS, and nobody notices for a month.

#### `/store/thanks` is marked at the container, not field by field

Replay is already denied for this route, but **autocapture still runs there**, and autocapture
reports the text of whatever a person taps. The page prints an email address, an order number and a
delivery address, so tapping any of them would otherwise land it in an event.

The class goes on the **page container**, not on the individual rows, and the reasoning is the same
as denying the whole route rather than masking its nodes: a per-field list is correct today and
quietly wrong at the next edit, when somebody adds a row to the order summary without thinking about
analytics.

`ph-no-capture` is the right class, and that was **verified in the SDK rather than assumed** — the
name was nearly got wrong. posthog-js's `io()` walks an element's ancestors and bails on
`ph-sensitive` or `ph-no-capture`; the similarly-named `ph-no-autocapture` is something else (the
default `css_selector_ignorelist`). And `ph-mask` appears **nowhere** in the SDK — which is correct,
because it is our own selector handed to rrweb through `maskTextSelector`, not a name PostHog knows.
